### C1 — Renderer never gets an initial `shell:visibility`, so a hide during startup leaves the render loop running behind a hidden window
- **File:** `apps/desktop/src/main/index.ts:43` (send site) and `:90` (the unused resync point)
- **Severity:** Important — spec §4.6 requirement missed
- **Description:** `sendToPet(pet, Channels.shellVisibility, …)` at index.ts:43 is the *only* `shell:visibility` send in the repo, and it is reachable only from `applyVisibility()`, which runs only from event handlers. There is no initial push and no resync when the renderer finishes loading. The renderer subscribes at `apps/desktop/src/renderer/pet/main.ts:100`, i.e. **after** `await Live2DStage.create(...)` at :14, and calls `stage.start()` unconditionally at :17. `apps/desktop/src/preload/pet.ts:12-17` registers `ipcRenderer.on` lazily, per `window.ds.on()` call, so no listener for `shell:visibility` exists during the whole document-load + model-load window. Electron drops such a send; it does not buffer. `index.ts:90` handles `stage:ready` with a bare `console.log` and sends nothing back.
- **Evidence:**
  - Repo-wide grep: `Channels.shellVisibility` has exactly one sender (`index.ts:43`).
  - `index.ts:90` — `onFromPet(Channels.stageReady, (info) => console.log('[pet] stage ready', info));`
  - The damage is real only because `apps/desktop/src/main/pet-window.ts:33` sets `backgroundThrottling: false` (spec §4.6, line 158 mandates it). That trips Electron's `disable_hidden_` path: the widget never goes hidden, the compositor keeps producing BeginFrames, and `requestAnimationFrame` keeps firing while the native window is hidden. `packages/stage/src/ticker.ts:31-41` is a pure rAF pump with no page-visibility fallback (repo-wide grep for `visibilitychange`: zero hits). So a dropped `hidden:true` leaves 30 fps of GL work rendering behind a hidden window.
  - Spec §4.6 line 157-158: "Hidden entirely (window hidden, **ticker stopped**)…".
  - Triggers with no timing constraint at all: `lock-screen` / `suspend` (launch, walk away, Win+L) and the tray hide item, all of which can fire inside the load window.
- **Suggested fix:** in the `stage:ready` handler (`index.ts:90`), send the current `{ hidden: visibility.hidden, reason: visibility.reason }` back to `event.sender`, making stage-ready the state-resync point. One line; also covers any future renderer reload.
- **Verifier reasoning (condensed):**
  - **V1 — real, Important.** Verified the three code facts independently and attacked the strongest refutation ("Chromium stops rAF for a hidden window anyway"). Not Critical: the state self-heals at the next `hidden:false` (and `Ticker.start()` guards `running`), so damage is bounded to one hidden interval.

Downgraded on reachability: at a normal launch the foreground is Explorer/Start/terminal, which is not display-covering and is excluded at `foreground.ts:19`, so nothing is dropped; autostart is Phase 4; there is no reload path in Phase 1. Also ruled the addendum §0 resource-budget citation non-binding (it does not name Phase 1) — **spec §4.6 alone carries the requirement**. Symptom is invisible and self-limiting.
  - **Adjudication:** kept at Important. Both verifiers agree the mechanism, the requirement (spec §4.6) and the one-line fix; they differ only on how often it is hit. ### C5 — Gaze easing speed changes with the 30→60 fps hover switch; spec §4.3's `GazeDriver` and "~250 ms" were never implemented
- **File:** `packages/stage/src/companion-model.ts:301` (`setGaze` → `setDragging`)
- **Severity:** Important — a named spec component missing and a performance knob mutating behaviour
- **Description:** `setGaze` delegates to `CubismUserModel.setDragging` → `CubismTargetPoint`, driven once per *rendered frame* by `CubismLookUpdater.onLateUpdate` (registered at `companion-model.ts:188`). `CubismTargetPoint.update` scales its **acceleration** by delta time but advances **position** by a per-call constant: `maxV = 4.0 / FrameRate(30) = 0.1333` and `this._faceX += this._faceVX` has no `deltaTimeWeight` term. Terminal gaze speed is therefore 0.1333 units per *call*, not per second. `apps/desktop/src/renderer/pet/main.ts:28` flips `stage.setFps(inside ? 60 : 30)`, and `packages/stage/src/ticker.ts` implements `setFps` by skipping rAF callbacks, so `tick()` truly fires 30×/s vs 60×/s — the same gesture animates at a different speed depending on a CPU-saving setting. Blink and breath were checked and *are* correctly dt-based (`cubismeyeblink.ts:86`, `cubismbreath.ts:56`), so gaze is the only frame-count-driven layer.
- **Evidence:**
  - `vendor/CubismWebFramework/src/math/cubismtargetpoint.ts:44` — `const maxV = (faceParamMaxV * 1.0) / FrameRate;` (per call); `:57-62` — `deltaTimeWeight` feeds only `maxA`; `:119-120` — `this._faceX += this._faceVX; this._faceY += this._faceVY;` with no dt term.
  - **Magnitude corrected by simulation** (both verifiers ported `update()` verbatim and ran it; the finding's "2×, 0.50 s vs 0.25 s" is a terminal-velocity idealisation that ignores the dt-correct accel/decel ramp). Measured settle to |error| ≤ 0.01: full −1→+1 sweep **0.633 s @30 fps vs 0.383 s @60 fps** (ratio ~1.65×); half sweep 0→+1 **367 ms vs 250 ms**; small move 0→+0.2 **133 ms vs 100 ms**. Neither rate meets "~250 ms" on a full sweep; 60 fps hits it exactly on a half sweep.
  - Spec §4.3 literally: "GazeDriver eases toward the target (critically damped, ~250 ms)". Spec line 51 names `GazeDriver` as a component of `packages/stage`; `MouthDriver`/`TextMouthDriver` were built as named, **`GazeDriver` does not exist anywhere in the repo**.
  - Live in every session: `apps/desktop/src/main/cursor.ts:21` polls at 30 Hz and sends `gaze:cursor` → `renderer/pet/main.ts:88` → `stage.ts:230` `setGaze` → `companion-model.ts:302`.
  - No gaze test exists in the suite.
- **Suggested fix:** build the `GazeDriver` the spec and §2.1 name and stop using `_dragManager` for gaze: a dt-based critically damped filter (`x += (target - x) * (1 - exp(-dt/tau))`, tau ≈ 0.08 s for ~250 ms settle) written into `CubismLook` via a small `ICubismUpdater`. **Note:** the cheap stopgap (call `update()` with a fixed 1/30 s step, accumulating leftover time) makes it fps-independent but locks in the 30 fps timing (~633 ms full sweep) and therefore does **not** satisfy §4.3.
- **Verifier reasoning (condensed):**
  - **V1 — real, graded Minor.** Confirmed the mechanism line by line and measured the corrected magnitudes above. Downgraded on three grounds the finding did not weigh: (i) the binding Phase-1 gaze requirement is arguably addendum D3, which names P1 explicitly — "Gaze: smoothed cursor-follow (head 30° / eyes 1.0 / body 10°) … (P1 has follow; saccade/rest are P3)" — with no timing figure, and `companion-model.ts:181-187` sets exactly those values; (ii) `plan:2271` rules the design explicitly ("easing is done by CubismTargetPoint inside the Framework") and `plan:828` specifies `setGaze` "wraps setDragging", so the implementation conforms to an accepted design; (iii) Phase-1 user impact is small — the fps flip fires only on hover, and once hovered the cursor is inside the silhouette so remaining travel is short (~30 ms difference, imperceptible); the full sweep only ever runs at 30 fps and reads as a natural head turn. Flagged that it becomes visible from Phase 2, since addendum line 19 raises the ticker to 60 Hz while a bubble is animating or the pet is speaking.
  - **V2 — real, Important, upheld.** Verified the same mechanism and measured the same numbers, then defeated three refutations: (i) **reachability** — the path is live in every session via the 30 Hz cursor poll; (ii) **requirement** — spec §4.3 states the 250 ms figure and spec line 51 names the `GazeDriver` component, addendum D3 keeps "smoothed cursor-follow" in P1 and relaxes nothing, and the plan discloses the substitution at `:2271`/`:828` but **never restates the 250 ms number and gates no acceptance criterion on gaze timing** — a lower authority silently dropping a binding figure; (iii) **not deferred** — grep of `progress.md` for "gaze" returns only the T4-T5 interface row (line 15), the Task 3 `toView` ruling (line 37) and Task 6's hover requirement (line 60); ledger precedent (Task 3, Task 6 ×6, Task 8) is that plan-mandated defects get fixed, not excused. Severity rests on two counts: a binding spec requirement missed (the named component was never built), and a **performance knob mutating behaviour**, which addendum §0's "60 Hz while a bubble is animating or the pet is hovered/speaking" makes worse in Phase 2 (her head visibly speeds up while she talks).
  - **Adjudication:** kept at Important on V2's spec-citation argument, which V1 did not address (V1 leaned on D3 as the binding requirement but D3 does not supersede §4.3 — it adds angles, it does not remove the timing figure).
